# KeystoneOS OKR-Driven Morning Cockpit — Design Spec

**Date:** 2026-06-12
**Status:** Draft — awaiting Eric review before planning
**Builds on:** 2026-06-12 "Federation, Made Operational" + the Phase-1/2 command-center work

---

## Problem / intent

Eric opens his laptop each morning and works whatever project is on his mind. He wants a **command center he opens first** that (a) puts OKRs front and center so they get daily attention, (b) tells him where to start / what's stale, (c) lets him dive into any project with full context, and (d) leaves room to spin up ad-hoc one-offs, take them to MVP, and move on.

Jack Roberts' "command center" framing integrates token spend, projects, skills, and agents. KeystoneOS already has the **projects** pillar and a basic dashboard. This spec builds the **OKR-driven triage core** — the daily driver — and defers the other pillars.

## Decisions locked (this session)

- **Daily job = Option A:** OKR-driven morning triage cockpit (chosen over spend-monitoring / pure launchpad / ambient status).
- **Linkage = A:** projects carry an `okr` tag in `projects.json` (machine registry owns the link). The vault's `okrs.yaml` stays hand-edited and is never written by KeystoneOS.
- **Layout = A:** vertical OKR-first briefing — hero scoreboard → "start here today" → project lanes grouped by KR → ad-hoc quick-start lane.
- **OKR source of truth = `SecondBrain\Projects\okr-tracker`** (`okrs.yaml` + `okr.py`). KeystoneOS consumes it; it does not reinvent OKR logic.
- **Scope = YAGNI:** token-spend, skills, and agents panels are deferred to later milestones (tracked in the roadmap below).

## Non-goals

- No server / live socket. Static, regenerated, file-backed (consistent with the 2026-06-10 decision).
- No writing into `okrs.yaml`. KeystoneOS only *reads* OKR data. The only change to okr-tracker is an additive JSON export.
- No moving or copying project files.

## Architecture

### 1. OKR data bridge (reuse okr-tracker)

`okr.py` already parses `okrs.yaml` into a dict and generates `SCOREBOARD.md`. Add:
- A `--json` flag (and/or `json` subcommand) that prints the structured data to stdout.
- On every normal report run, **also write `okrs.json`** beside `SCOREBOARD.md` (objectives; key_results each with `id`, `objective`, `text`, `target`, and the **latest check-in**: `status`, `confidence`, `next_action`, `blocker`, `date`; plus `meta.cycle` and `meta.gate`).

KeystoneOS adds `Get-OkrData` that reads `okrs.json` at `<OKRs project canonicalPath>\okr-tracker\okrs.json` — i.e. derived from the existing `OKRs` registry entry (`SecondBrain\Projects`) plus the `okr-tracker` subdir, so there is no new hard-coded path. **No Python dependency at render time** — KeystoneOS reads the JSON artifact. If `okrs.json` is missing or older than `okrs.yaml`, the cockpit renders with a "⟳ refresh OKRs (run okr.py)" nudge instead of failing.

### 2. Project ↔ OKR linkage

- `projects.json`: optional `okr` field, a string array of KR ids (e.g. `["1.2"]`); default `[]`. Back-compat: absent → untagged.
- New command `keystone okr-link <Key> <KR-id> [<KR-id> ...]` writes the tag into `projects.json` and auto-commits (same pattern as `heal`).
- Untagged projects render in a "General / unlinked" lane.

### 3. Cockpit renderer (Layout A)

New `New-CockpitHtml` (reusing the existing dashboard CSS/infra) → `outputs/dashboard/cockpit.html`, sections top-to-bottom:
- **Hero — OKR scoreboard:** per objective, per KR: status pill (🟢🟡🔴✅), confidence bar, `next_action`, `blocker`; gate countdown to `meta.gate` (Aug 31).
- **Start here today:** derived triage list — 🔴 KRs first, then the stalest check-in dates — each line is the KR's `next_action`, linking to the project(s) serving that KR.
- **Project lanes:** grouped under the KR they serve (from the `okr` tag); each project card links to its existing launch page (which carries the Phase-2 `context` payload). Unlinked projects in a General lane.
- **Quick-start lane (ad-hoc v1):** a documented quick-start command + a list of recent **unregistered** DEV folders (from the existing `inventory` scan, minus registry keys) so one-offs spin up fast without full promotion.

New command `keystone cockpit` renders it; it is also regenerated by `morning` / `today` / `dashboard`.

### 4. Daily wiring

The morning cadence already regenerates the dashboard — it now also regenerates the cockpit. `keystone cockpit` rebuilds on demand. Static file output; open `cockpit.html` in the browser.

## Components & boundaries

| Unit | Responsibility | Depends on |
|---|---|---|
| `okr.py --json` / `okrs.json` | Expose OKR data as JSON; stay the source of truth | `okrs.yaml` |
| `Get-OkrData` (keystone.ps1) | Read `okrs.json`; report staleness | `okrs.json` |
| `okr` field + `okr-link` cmd | Link projects → KRs | `projects.json` |
| `New-CockpitHtml` + `cockpit` cmd | Render Layout A | `Get-OkrData`, `Get-Projects`, inventory, Phase-2 launch pages |
| morning/today/dashboard | Regenerate cockpit on cadence | `New-CockpitHtml` |

## Acceptance criteria

- [ ] `python okr.py --json` emits valid JSON containing objectives and KRs with latest-checkin `status`/`confidence`/`next_action`/`blocker`; a report run also writes `okrs.json`.
- [ ] `keystone okr-link FaceComps 1.2` adds `"okr": ["1.2"]` to that project; re-run is idempotent; untagged projects unaffected.
- [ ] `keystone cockpit` produces `cockpit.html` containing: every objective, every KR with status + next_action, a "Start here" list led by 🔴 KRs, project lanes grouped by KR, and a quick-start lane.
- [ ] A project with no `okr` tag appears in the General lane (no crash).
- [ ] Missing/stale `okrs.json` → cockpit renders with a refresh nudge (no crash).
- [ ] `keystone morning` regenerates the cockpit.
- [ ] Full existing test suite stays green.

## Testing

- Run all `tests/*.ps1` green before/after.
