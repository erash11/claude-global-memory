## What today was about

Two threads ran in parallel, plus a maintenance thread.

**1. Scheduled-job durability (KeystoneOS).** Jobs were failing silently. The root
cause was that nothing recorded whether a job *succeeded* — Task Scheduler's own
history was the only record, and it reports process exit, not outcome. On 7/27 it
logged the morning cadence as "successfully completed" with a return code that
actually meant *killed mid-run*. Fixed by declaring jobs in `data/jobs.json` and
running them only through `scripts/run-job.ps1` (per-job lock, timeout, recorded
outcome), with `scripts/keystone-reconcile.ps1` checking the scheduler against a run
ledger.

**2. CFB Victory Model weekly capture.** Built the data pull, the weekly forecast
freeze, and a reminder so the ritual doesn't get missed. The forecast is
**not backfillable** — the published Power BI report overwrites weekly and keeps no
history, so a missed Wednesday is gone permanently. That constraint drove everything
else about the design.

**3. Maintenance.** Meeting corpus naming finished, skill descriptions trimmed,
backup rescheduled, evening debrief.

## Decisions made — and the reasoning that would otherwise be lost

**Backup moved 06:15 → 00:30.** The open question was whether a 00:30 task would fire
at all: the machine is in Modern Standby or off every night, with zero power
transitions between 00:00 and 06:00 across the prior 8 days. Friday 7/24 settled it —
tasks queued overnight ran on wake, so `WakeToRun` is not needed. Do not "fix" this
later by adding `WakeToRun`; it was considered and rejected.

**Power BI `modelsAndExploration` endpoint: abandoned deliberately.** Reaching it
required spoofing `Origin` and `Referer` to look like `app.powerbi.com`. The
permission classifier blocked it and that was the right call. `weekly_capture.py`
instead loads the *published* report as a browser and reads the rendered table.
**Do not revive the API approach.**

**`/forecast-capture` asks no questions.** Baylor, 2026, and the output paths are
fixed. A skill that prompted every Wednesday would be fifteen identical answers over
a season.

**Season window is the real calendar, not the season.** `cfb_season_start =
2026-08-26` — the Wednesday *before* the first Saturday games, because starting on
Aug 29 would have missed the Week 1 freeze. `cfb_season_end = 2027-01-23`. That's 22
capture Wednesdays; the last useful one is Jan 20.

**An untagged meeting is a signal, not a bug.** Two Saturday meetings exported with
zero tags. The auto-tagger was working correctly — it had no topic to match. That
means the taxonomy is behind the work, so `book-project` and `ministry-formation`
were added to `data/meeting-topics.json`.
